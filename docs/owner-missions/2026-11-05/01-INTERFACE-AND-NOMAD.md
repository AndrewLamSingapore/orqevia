# ABEX MASTER MISSION
## ORQEVIA — TOTAL INTERFACE REPLACEMENT & PROJECT NOMAD CAPABILITY ASSIMILATION

**Mission classification:** Full-system transformation  
**Target:** Orqevia  
**Reference:** Project NOMAD by Crosstalk Solutions  
**Execution:** Autonomous, evidence-driven, end-to-end  
**Final objective:** One unified, production-ready Orqevia experience with a completely replaced interface, selectively assimilated NOMAD capabilities, and no surviving legacy governance architecture.

---

# 1. PRIMARY DIRECTIVE

Abex, execute a comprehensive transformation of Orqevia.

The current Orqevia interface is to be fully retired and replaced with a new unified interface inspired by the Project NOMAD Command Center.

This is not a superficial reskin.

It is a coordinated frontend replacement, capability-discovery exercise, architectural simplification, and operational modernization.

The new Orqevia must combine:

1. Project NOMAD's visual simplicity and distinctive design.
2. Orqevia's existing autonomous intelligence and multi-agent capabilities.
3. Valuable operational patterns discovered in NOMAD's source repository.
4. A radically simplified, adaptive execution architecture.
5. Complete removal of obsolete PRIME-era governance and frontend structures.
6. Preservation and improvement of every legitimate, functioning Orqevia capability.

**The finished system must be simpler to operate, more powerful, more adaptive, and less bureaucratic than the existing implementation.**

Do not create another governance organization.

Do not introduce competing intelligence hierarchies.

Do not preserve obsolete structures merely because they already exist.

Do not equate autonomy with unrestricted authority. Preserve necessary security, financial boundaries, user permissions, and recovery mechanisms without turning them into bureaucratic approval chains.

# 5. PROJECT NOMAD CAPABILITY SWEEP

Perform a comprehensive source-level audit of Project NOMAD.

For each discovered feature, determine:

1. What it actually does.
2. Where it is implemented.
3. Its dependencies.
4. Its operational assumptions.
5. Whether Orqevia already has an equivalent.
6. Whether the NOMAD implementation is superior.
7. Whether it can be reused directly.
8. Whether it should instead be adapted or reimplemented.
9. Its security implications.
10. Its ongoing maintenance burden.
11. Its measurable value to Orqevia.

Classify every meaningful discovery as:

- **Adopt:** Valuable and compatible.
- **Adapt:** Valuable concept requiring Orqevia-specific implementation.
- **Already present:** Retain or improve existing implementation.
- **Reject:** Duplicative, obsolete, incompatible, or unnecessary.
- **Investigate:** Insufficient evidence.

Do not install everything simply because it exists.

# 6. PRIORITY CAPABILITY ASSIMILATION

## 6.1 Orqevia Supply Depot

Investigate NOMAD's application and container management system.

Develop an Orqevia-native capability depot supporting:

- Tool discovery.
- Agent capability packages.
- Service installation.
- Container lifecycle management.
- Dependency inspection.
- Resource requirements.
- Version visibility.
- Logs and diagnostics.
- Health monitoring.
- Updates and rollback.

Investigate NOMAD's use of:

- Kiwix.
- ZIM archives.
- Ollama.
- Qdrant.
- Offline documentation.
- Local knowledge collections.
- Retrieval-augmented generation.

Determine how these can strengthen Orqevia's existing memory and retrieval systems.

Target capabilities:

- Offline knowledge access.
- Local semantic retrieval.
- Shared knowledge across authorized agents.
- Document indexing.
- Source attribution.
- Incremental updates.
- Knowledge freshness tracking.
- Storage-efficient collections.

Do not create duplicate vector databases or memory systems without a demonstrated advantage.

## 6.3 Hardware-aware intelligence runtime

Investigate NOMAD's system benchmarking and hardware visibility.

Extend the concept into Orqevia-native resource awareness.

Measure:

- CPU availability.
- RAM usage.
- GPU capabilities.
- VRAM availability.
- Disk capacity.
- Storage throughput where useful.
- Network availability.
- Model execution performance.
- Agent workload.
- Service contention.

Use this information to improve workload placement and model selection.

The system should distinguish between tasks suitable for local execution and those requiring external models.

Optimize for useful completed work, not maximum resource consumption.

## 6.4 Offline-first resilience

Investigate NOMAD's offline operation.

Enable Orqevia to retain useful local capabilities during connectivity interruptions.

Consider:

- Local models.
- Local knowledge.
- Local task execution.
- Durable mission state.
- Recoverable queues.
- Graceful degradation.
- Deferred synchronization.

Do not promise full offline functionality for services that inherently require external connectivity.

## 6.5 Intelligent setup and configuration

Study NOMAD's setup wizard.

Develop hardware and environment discovery where it materially reduces setup complexity.

Automate safe configuration defaults.

Avoid unnecessary setup screens and repeated questions.

## 6.6 Service management and recovery

Investigate NOMAD's container-management, update, monitoring, and recovery patterns.

Adopt useful mechanisms for:

- Service health.
- Restart behavior.
- Failure diagnosis.
- Version management.
- Controlled updates.
- Rollback.
- Configuration validation.
- Resource monitoring.

Preserve durable recovery without recreating governance bureaucracy.

## 6.7 Knowledge packs and specialized utilities

Evaluate NOMAD's content collections, documentation, CyberChef integration, maps, and other utilities.

Integrate only where they enable real Orqevia missions.

For example, maps should support genuine geographic tasks rather than become a decorative dashboard module.

### Stage D — Simplify

### Stage G — Retire

After successful verification, remove obsolete interface assets, routes, and dead code.

Ensure the retired interface cannot accidentally reappear.

# 10. AUTONOMOUS EXECUTION RULES

Abex should execute independently within existing legitimate authority.

Avoid asking for approval at every intermediate step.

Make reversible engineering decisions autonomously.

Use parallel agents where their work can be independently verified and merged safely.

Do not create unnecessary committees, reviewers, or governance agents.

Escalate only when an action requires authorization that has not been granted, creates a material irreversible risk, or involves significant financial or security consequences.

In particular:

- Never expose or rotate production secrets casually.
- Never execute financial transfers without appropriate authorization.
- Never destroy irreplaceable user data.
- Never weaken security boundaries merely to remove governance.
- Never perform an irreversible production migration without a tested recovery path.
- Never silently disable a functioning critical capability.

Where uncertainty exists, gather evidence and select the lowest-risk effective path.
