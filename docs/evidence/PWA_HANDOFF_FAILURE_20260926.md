## Reproduction and rejection decision

The production request was reproduced against the same endpoint with this browser-navigation shape:

```text
GET /pwa/ HTTP/1.1
Host: 192.168.1.23:8443
Sec-Fetch-Site: cross-site
Sec-Fetch-Mode: navigate
Sec-Fetch-Dest: document
Referer: https://authority-engine-app.vercel.app/jarvis
User-Agent: representative iPhone Safari string (synthetic, not claimed as the physical phone's exact value)
```

That shape returned the same HTTP 403 and `PWA_REQUEST_REJECTED`. Changing only `Sec-Fetch-Site` to `none` returned the PWA HTML shell with HTTP 200.

The exact production predicate was `origin_valid()` in `app/pwa_sessions.py`: after validating the configured HTTPS origin, request base URL and optional Origin header, it rejected every request whose `Sec-Fetch-Site` was `cross-site` or `same-site`. It did not distinguish a safe top-level human document navigation from an API request. The middleware caught that HTTP 403 and deliberately replaced its detail with `PWA_REQUEST_REJECTED`.

## Narrow repair contract

Only a request satisfying every condition below may cross the Fetch Metadata site boundary:

- method is `GET`;
- path is exactly `/pwa/` or `/pwa/index.html`;
- `Origin` is absent;
- `Sec-Fetch-Mode` is `navigate`;
- `Sec-Fetch-Dest` is `document`;
- the configured HTTPS scheme, host and port still match exactly.

Cross-site API requests, Interface requests, writes, PWA asset requests, requests with a foreign Origin, host mismatches and caller-supplied identity/authorization headers remain rejected. The launch page cannot enroll a device, create an identity, change a role or perform an objective.
